---
description: Cut a new release if there are unreleased completed features (test, commit, push, tag, publish)
allowed-tools: Bash, Read, Edit
---

Release the next version of StickyNotes if — and only if — there is shippable work
on `main` that has not been tagged yet. Be cautious: don't tag a release for a
WIP branch, don't skip tests, don't push without verifying the working tree.

## 1. Verify there's something to release

Run these in parallel and stop if any check fails:

- `git rev-parse --abbrev-ref HEAD` — must be `main`. If not, ask user before continuing.
- `git fetch --tags origin` — make sure local tags are current.
- `git log --oneline $(git describe --tags --abbrev=0)..HEAD` — list commits since
  the most recent tag. **If empty, stop and tell the user there's nothing to release.**
- `git status --short` — note any uncommitted work; surface it to the user before
  bundling it into the release.

Read the commits since the last tag and judge whether they represent **completed
features or fixes** worth a release. Casual WIP / debugging commits → ask the user
to confirm. Don't release just because commits exist.

## 2. Pick the version

Look at the latest tag (e.g. `v0.5.2`) and the nature of the unreleased commits:

- Bug fixes / small tweaks only → bump patch (`v0.5.2` → `v0.5.3`)
- New user-facing feature → bump minor (`v0.5.2` → `v0.6.0`)
- Breaking change → bump major (`v0.5.2` → `v1.0.0`)

Tell the user the proposed version and the one-line summary of what's in it.
**Wait for confirmation before tagging or pushing.**

## 3. Test

- `swift build -c release` — must succeed cleanly.
- `swift test` if a test target exists (check `Package.swift`); otherwise skip.
- If there are uncommitted changes the user wants in the release, stage and commit
  them with a descriptive message *before* tagging. Never tag on top of a dirty tree.

## 4. Push and tag

In order (each must succeed before the next):

1. `git push origin main` — push commits first so the tag points at a public sha.
2. `git tag -a vX.Y.Z -m "vX.Y.Z"` — annotated tag at HEAD.
3. `git push origin vX.Y.Z` — push the tag.

## 5. Publish the release

Run `./scripts/release.sh vX.Y.Z`. That script builds the `.app`, packages
`.dmg` + `.zip`, and creates the GitHub release with autogenerated notes via `gh`.

If the script fails partway, stop and report — don't retry blindly. The tag may
already be pushed; deleting it requires `git push origin :refs/tags/vX.Y.Z` and
should only happen with the user's go-ahead.

## 6. Report

Print the release URL (`gh release view vX.Y.Z --web` will give it) and the list
of commits the release covers, so the user can confirm.

---

Notes:
- Never use `--no-verify`, never force-push.
- Don't bump versions in source files unless a file already contains a version
  string — this project's version lives only in git tags + the GitHub release.
